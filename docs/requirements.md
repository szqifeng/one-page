# 季度双周滚动规划系统需求说明

## 1. 产品目标

为产品、开发、运营等混合团队提供季度视角的双周滚动规划，统一维护人员容量、DPO/日常投入比例、事项交付、人天、迭代和权限，并支持团队级数据隔离、登录审计和历史备份恢复。

## 2. 核心业务对象

- 团队：用户、人员、角色、规划、备份和日志的数据隔离边界。
- 用户：登录主体，可通过本地账号或 OAuth2 创建。
- 人员：参与规划的团队成员，与登录用户通过账号关联。
- 人员类型：产品、开发、运营等工作属性。
- 权限角色：定义用户在团队内可执行的操作。
- 迭代：季度内的双周时间段，包含开始和结束日期。
- 事项：DPO 或日常需求，可跨迭代填写阶段交付、人天和 0–100% 完成进度。
- 规划备份：每日三个定时快照，用于历史恢复。

## 3. 功能需求

### 3.1 登录与用户

- 登录方式由 `AUTH_MODE` 配置为 `local`、`oauth2` 或 `both`。
- OAuth2 参数必须由环境变量提供。
- OAuth2 登录通过 profile 接口读取 `email`，取 `@` 前内容作为账号。
- OAuth2 用户不存在时自动创建，默认角色为“未授权用户”，不获得团队权限。
- 会话使用服务端保存的随机令牌和 HttpOnly Cookie。

### 3.2 团队与权限

- 所有业务数据按团队隔离。
- 管理员可维护人员、人员类型、权限角色和迭代。
- 普通成员仅能编辑负责人为自己的事项，服务端必须再次校验，不能只依赖前端按钮。
- 未授权用户不能查看或修改团队规划。
- 迭代维护包含添加、编辑、设为当前和删除操作；当前迭代或已有投入的迭代不可删除。

### 3.3 规划看板

- 支持创建和切换不同季度；每个自然年最多 3 个季度，各季度的迭代、事项和投入相互独立。
- 新建季度时配置名称、年份、开始和结束日期，系统自动生成连续双周迭代；同年季度日期不可重叠。
- 展示季度、双周迭代、人员、事项、交付、人天、状态和剩余容量。
- DPO 与日常事项均包含完成进度，范围为 0–100%。
- 支持按负责人、人员类型、需求类型、状态和关键字筛选。
- 支持人员分组一键展开和折叠。
- 每个人可独立配置 DPO 与日常比例，两项合计为 100%。
- DPO 已排、日常已排和季度总投入卡片可打开“人员 × 迭代”二维容量表。
- 容量表展示已排、参考容量和可用容量；比例为 0 的人员不出现在对应类型表中。

### 3.4 备份与恢复

- 系统按 `BACKUP_TIMES` 每日执行三次团队规划快照，默认 `02:00,10:00,18:00`；配置必须是三个互不重复的有效时间，否则使用默认值。
- 调度时区由 `BACKUP_TIMEZONE` 配置，默认 `Asia/Shanghai`。
- 同一团队、日期和备份时点只能生成一份快照。
- 恢复窗口展示最近 50 份备份。
- 恢复不会删除历史备份；恢复后的规划作为新的当前数据版本保存。
- 仅具备全部规划维护权限的用户可以查看和执行恢复。

### 3.5 行为日志

- 记录登录、退出、规划读取、规划写入、恢复和其他已登录 API 请求。
- 日志包含团队、用户、行为、请求方法、路径、状态码、IP、User-Agent 和耗时。
- 仅具备权限管理权限的用户可以查看最近的行为日志。

## 4. 非功能要求

- PostgreSQL 是唯一持久化数据源，不使用浏览器 localStorage 保存业务数据。
- 规划写入使用版本号乐观锁，冲突时返回 409，避免静默覆盖。
- 服务提供 `/api/health` 健康检查。
- 应用使用 Docker Compose 部署，包含 PostgreSQL、API 和 Nginx 前端。
- 密码、OAuth2 Client Secret 和数据库密码不得写入代码或提交到 Git。
